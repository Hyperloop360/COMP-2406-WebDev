Paws & Claws - COMP2406 Assignment 2: Server-side programming with AJAX
==========================================================================

HOW TO RUN
----------
    node server.js
Then open http://localhost:3000/ . No installation is needed (only the built-in
http, fs, path and url modules are used). The server loads every .json file in
data/shelters/ first and only starts listening once that has finished. Dropping an
additional shelter .json file into that folder (same format) requires no code changes.
Applications are kept in RAM only, so restarting the server empties the list.
This project is built on my own Assignment 1 solution.

URLS
----
Pages:   /   /browse   /browse?shelterId=sn   /details?petId=pn&shelterId=sn
         /apply?...    /applications   /about
Data:    GET  /shelters                          basic shelter info (no pets)
         GET  /shelters?id=sn                    full shelter (with pets) or 404
         GET  /shelters/pets?petId=&shelterId=   one pet, or 404
         POST /submitapplication                 JSON body; stores the application
         GET  /applications-data                 JSON array summarizing all applications
         PUT  /applications-update               {applicationId, status}
         GET  /applications-details?id=a4        full application, or 404

DESIGN DECISIONS BEYOND THE REQUIREMENTS
----------------------------------------
Server
- Static files are only served from /styles, /js and /images. server.js and the raw shelter .json
  files cannot be downloaded, and ".." paths are rejected.
- POST/PUT bodies are validated: bad JSON or an unknown pet/shelter returns 400, an invalid status
  returns 400, and an unknown application id returns 404. Only known application fields are stored.
  Bodies larger than ~1MB are refused.
- Shelters are sorted by id (s1, s2, ...) so the drop-down order is stable.
- /applications-data returns only the summary fields; the applicant's personal details are only
  available from /applications-details.

Browse / details / apply pages
- If the user changes shelters quickly, a late response for an old shelter is ignored.
- Parrots stay grouped under the "Birds" button and unknown types under "Other" (as in A1).
- Fetch errors (e.g., server unreachable) are shown on the page instead of failing silently.
- "Back to Browsing" re-selects the shelter; the type button is reset to "All".
- The Submit button is disabled while the request is in progress, and the "Application Submitted!"
  message is only shown after the server confirms it received the application. If the server
  rejects it, an error is shown and the form is kept so nothing typed is lost.
- Text coming from the URL is inserted with textContent so it can never be treated as HTML.
- As in A1, the form's required fields are checked (reportValidity) when Submit is pressed.

Applications page
- Status drop-downs and the status badge are colour-coded: Unprocessed = grey, Pending = yellow,
  Rejected = red, Approved = green. If a status update fails on the server, the drop-down goes back
  to its previous value and an error message is displayed.
- Applicant-entered text is inserted using textContent, so it can never be interpreted as HTML.
- View buttons toggle (only one at a time) and use the site's teal/orange nav colours. The details
  are four cards: Application, Pet Requested (with image), Applicant and Household. Changing the
  status while a card is open updates the card too.
- The applicant details and the pet data are requested at the same time (async/await).
